# 音视频基础

* auto-gen TOC;
{:toc}

这一页讲**视频到底以什么形态到达浏览器**，以及这些形态各自意味着什么。

网页上看到的「一个视频」，在网络上可能是 5 种完全不同的东西：一个完整的 MP4 文件、一张 `.m3u8` 目录加几十个 `.ts` 分片、一份 DASH 清单、只存在于浏览器内存里的一段段二进制，或者一个连文件名都不存在的 Blob 地址。把它们搞混，就会出现「下载下来的视频没有声音」「点 `.m3u8` 只拿到一个几十 KB 的文本文件」这类让人摸不着头脑的现象。

下面说的「本扩展」，指的就是 video-sniffer（视频嗅探下载器）这个 Chrome 扩展。它的全部工作，就是把这几种形态都认出来，然后还原成一个能看的文件。

在整章里的位置：这是 [章节总览](00-summary.md) 里的第 02 页，也是阅读路线 A 的第二步。读完 [扩展开发入门](01-extension-basics.md) 之后，先在这里补齐音视频的基本词汇，再进 [扩展架构：五个执行上下文](03-architecture.md) 去看这些数据是怎么被钩住的。

## 先把三个词搞懂

后面全靠这三个词，先打地基。

### 「文件」不是只有一种：容器和编码是两回事

你硬盘上的 `movie.mp4` 看起来是「一个文件」，其实它内部是**两层东西**：

```
movie.mp4  （外壳 / 容器 container）
├── 视频轨：画面数据，编码格式是 H.264
└── 音频轨：声音数据，编码格式是 AAC
```

打个比方：

- **编码格式**（H.264 / AV1 / VP9 / AAC / Opus）= **人的语言**。日语、英语、粤语，同一句话内容一样，编码方式不同。
- **容器格式**（MP4 / MKV / WebM / FLV / TS）= **信封 / 包装方式**。同一段对话，装在不同的信封里。

所以你会听到这样的话：「这个视频是 H.264 编码的」「这个是 MKV 容器」——它们说的不是一件事。

**为什么插件要「转 MP4」？**

因为不是所有网站都给 MP4。B 站给的是分片、腾讯视频给的是 FLV、YouTube 给的是 WebM。
而 MP4 是兼容性最好的容器（Windows 播放器、手机、剪辑软件都认）。
所以插件要做的事情叫**封装（remux）**：把里面的音视频「原样」取出来，装进 MP4 信封里。

> **关键区别：封装 ≠ 转码。**
>
> - **封装**：内容一个字节都不改，只是换个信封 → **快、无损**。本扩展优先用这个。
> - **转码**：把画面重新「画」一遍（换一种语言重录） → 慢、有损、质量下降。
>
> 插件的做法是：**先试封装，封装不了才转码**。

封装这一步最终由谁来做、数据在管线里怎么流动，见 [扩展架构：一次下载的完整数据流](03-architecture.md)。

### 「轨道」= 分开的流

上面提到的「视频轨」和「音频轨」，在网络上是**两个完全独立的文件**。

这在 DASH 格式里特别常见：

```
https://cdn.xxx.com/40394753402-1-100026.m4s   ← 视频轨（只有画面）
https://cdn.xxx.com/40394753402-1-100008.m4s   ← 音频轨（只有声音）
```

**这解释了一个非常常见的困惑**：为什么从 B 站直接点一个 `.m4s` 链接下载，得到的视频**没有声音**？

因为那个链接只是画面。声音在另一个文件里。

插件的「DASH 条目」就是这一对文件的**组合**，点下载时会把两个都下下来，再合成一个 MP4。

番剧页的 DASH 长什么样，见 [B 站番剧 DASH 接口](05-bilibili-bangumi.md)；投稿页的 `durl` 和 DASH 又有什么不同，见 [B 站投稿视频下载](06-bilibili-ugc.md)。

### 「流」和「分片」：m3u8 其实是一张目录

「流」（stream）= 一段连续的数据。视频可以是一个大文件，也可以被切成很多小块。

「分片」（segment / fragment）= 被切开的小块。

为什么要切？

- **切了才能边下边看**。你不用等整部 2 GB 的电影下完才能开始看，下到哪播到哪。
- **切了才能切画质**。网络差的时候下低画质的片，网络好了换高画质的。
- **切了才能做「边播边录」**。播放到哪，记录到哪。

HLS 的典型切法（一集 24 分钟的番剧）：

```
index.m3u8          ← 一份"目录"，写着：
  seg0.ts           ← 第 1 块（约 4 秒）
  seg1.ts           ← 第 2 块
  seg2.ts
  ...
  seg350.ts
```

那个 `.m3u8` 文件**本身不含任何音视频数据**，它只是一张目录。
你点它下载，只会拿到一个几十 KB 的文本文件 —— 这就是本扩展 v1.4.0 修的一个具体问题（同类误报的排查见 [DASH 下载异常排查](09-troubleshooting.md)，番剧页上的修复细节见 [B 站番剧 DASH 接口](05-bilibili-bangumi.md)）。

清单该怎么解析、解析出来的东西怎么进资源表，见 [代码导读与项目结构](04-code-tour.md)。

## 网页上的视频到底是怎么送过来的

浏览器里看视频，实际有 5 种情况。本扩展必须全部认识，否则会漏掉或认错。

| 情况 | 你在页面上看到的 | 网络上实际传输的 | 磁盘上有文件吗 | 扩展里叫什么 |
|---|---|---|---|---|
| **① 整个文件** | `<video src=".../movie.mp4">` | 一个完整的 MP4 | 有 | `direct`（直链） |
| **② HLS** | 播放器自己在放 | 一份 `.m3u8` 目录 + 几十个 `.ts` | 有（分开的） | `hls` |
| **③ DASH** | 播放器自己在放 | 一份清单 + 独立视频轨/音频轨 | 有（分开的） | `dash` |
| **④ MSE** | 播放器自己在放 | 一段段二进制，边下边塞进内存 | **没有** | `mse` |
| **⑤ Blob** | `<video src="blob:https://...">` | 内存里的一个对象 | **没有** | `blob` |

### 情况 ④：MSE 是什么，为什么这么麻烦

MSE（Media Source Extensions）= 浏览器提供的一个接口，让**网页自己**把视频数据喂给浏览器：

```js
// 页面里的代码（伪代码）
const ms = new MediaSource();
video.src = URL.createObjectURL(ms);   // ← 指向一个"空的"内存对象
ms.addSourceBuffer('video/mp4; codecs="avc1.64001E,mp4a.40.2"');
// ...播放器一边从网络取数据，一边：
sourceBuffer.appendBuffer(chunk);      // ← 每次塞 2 MB 进去
```

这就像**水管**：不是先接一根完整的管子，而是水龙头一直流水，播放器边收边播。

**对下载的致命影响**：数据只存在于浏览器的内存里，硬盘上没有文件。
所以「点下载」最多只能拿到「已经缓冲的那部分」（比如前 55 秒）。

这就是为什么插件需要一个额外的模式：**「边播边录」** ——
在 `appendBuffer` 的钩子里把每一块数据**同时**转发出去另存，这样就能存下完整的一集。

YouTube 走的就是这条路，录制实测见 [YouTube 视频抓取](07-youtube.md)；`appendBuffer` 这类钩子要挂在哪个执行环境里，见 [扩展架构：五个执行上下文](03-architecture.md)。

### 情况 ⑤：Blob URL 是什么

`blob:https://www.bilibili.com/4d307fa5-0b7f-4ac7-b56e-e9486ce4e057`

这种地址看着像网址，其实不是。它是浏览器给你的一个**内存句柄**，指向一个存在内存里的对象。
页面关掉就没了。

所以插件必须**在它被创建的那一刻拦截下来**，否则之后就没法回头拿数据了。

同一个 blob URL 被音视频两条轨共用时的坑，见 [YouTube 视频抓取](07-youtube.md)。

### 一个关键的技术事实：地址藏在 JSON 接口里

B 站这类大站的视频地址，**从来不会出现在任何「视频响应」里**。

地址藏在**一个 JSON 接口**的返回里：

```
GET https://api.bilibili.com/ogv/player/pre/check/drm
→ {"code":0,"data":{"video_info":{"dash":{"video":[{...}],"audio":[{...}]}}}}
```

播放器拿到这个 JSON，才知道该去下哪个 `.m4s`。

所以光靠「监听网络下载了什么东西」是不够的 —— **必须去解析页面的 JSON 接口**。
这就是插件要挂钩 `fetch` 和 `XMLHttpRequest` 的原因。

这两个接口（B 站番剧页、投稿页）的真实返回结构，见 [B 站番剧 DASH 接口](05-bilibili-bangumi.md) 和 [B 站投稿视频下载](06-bilibili-ugc.md)；换到一个全新站点时怎么找到这个 JSON，见 [新站点适配手册](08-new-site-playbook.md)。
