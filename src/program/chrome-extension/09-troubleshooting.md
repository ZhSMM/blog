# DASH 下载异常排查

* auto-gen TOC;
{:toc}

下载番剧的时候，你可能遇到过两种看起来毫不相干的现象：文件只有 **20.9 MB**（明明是 24 分钟的一集），或者下下来的 MP4 打开是满屏条纹。这两件事在 v1.4.3 那次修复里被追到了同一批根因上——**拿到的根本不是你想下的那条流**。

这一页是整章的**兜底页**：它记录的是「下不动 / 下坏了」的时候，按什么顺序查、查出来是什么问题、该怎么修，面向想搞明白「为什么会这样」的同学。前面 [B 站番剧 DASH 接口](05-bilibili-bangumi.md) 讲了番剧的地址从哪来、[B 站投稿视频下载](06-bilibili-ugc.md) 讲了投稿视频怎么下；还没读过主线的，先看 [章节总览](00-summary.md) 挑一条阅读路线；要把这套排查搬到别的站点上，看 [新站点适配手册](08-new-site-playbook.md)。

本页出现的 `src/common/dash.js`、`src/background/bilibili-alt.js` 这类写法，**指的是 video-sniffer 项目里的文件**，不是本章的页面。

## 一句话结论

B 站番剧网页播放器用的 `ogv/player/pre/check/drm` 是 **DRM 协商接口**。
它给未登录/无权限的访客返回的是一份**占位清单**——
指向别的视频的文件、码率低到 121 kbps、画面是乱码。

**下载占位流 = 文件远小于实际大小 + 播放时满屏条码。**

修复办法：番剧页改用**普通播放接口** `x/player/wbi/playurl` 取地址，
那里给的是没加密、真实码率的流；同时在下载后再做一次「体检」，
发现占位流/加密流就自动换档并明确告知用户。

---

## 症状

| 用户看到的 | 技术上的含义 |
|---|---|
| 「下载的大小远小于实际大小」 | 24 分钟的集只有 20.9 MB |
| 「播放时为全屏条码」 | 画面是纯灰 + 噪点，解码器报 `concealing 8160 DC, AC, MV errors` |
| 有时又是正常的 | 取决于这一集/这个账号拿到的是哪一档流 |

**「时常出现」而不是「每次都出现」** 是这个问题的关键线索：
说明不是某段代码坏了，而是**拿到的流有好有坏**。

## 排查路线

排查这类问题，顺序很重要。**先确认拿到的是哪条流，再看体积，最后才看代码。**

### 第 1 步：确认拿到的是哪条轨

问三个问题：

1. 这个 URL 出现在哪个接口的返回里？
2. 清单里一共有几条轨？我选的是哪条？
3. 选轨的规则是什么？（是「码率最高」，还是「站点正在播的那一档」？）

> v1.4.3 之前的规则是**「码率最高的优先」**——
> 而 B 站恰恰把没权限的那一档标成了「码率最高」。这就是第一个坑。

### 第 2 步：看体积

用「实际字节数 ÷ 时长」算出**有效码率**，和分辨率对一下：

```
有效码率 = 文件字节数 × 8 ÷ 时长(秒)
```

| 分辨率 | 正常码率 | 占位流码率 |
|---|---|---|
| 1920×1080 | 2~6 Mbps | **121 kbps** |
| 852×480 | 500~900 kbps | **26 kbps** |
| 640×360 | 300~600 kbps | **23 kbps** |

差了一个数量级，一眼就能看出来。

### 第 3 步：抽帧看画面

「文件能播」不等于「文件对」。**抽一帧出来看看**是最直观的验证：

```bash
node tools/diagnose-dash-frames.mjs
# 会在 test/frames/ 下生成 PNG，直接看图
```

实测截图（番剧 1080P 占位流，第 60 秒）：

> 整屏灰色，左上角一小片噪点。

### 第 4 步：看 MP4 的盒子结构

用 `tools/dump-boxes.mjs` 把文件结构打出来，重点看四处：

```
moov
 └ trak
    └ mdia
       └ minf
          └ stbl
             └ stsd
                └ encv        ← 正常应该是 avc1
                   └ sinf     ← 保护信息
moof
 └ traf
    └ senc                    ← 采样加密（正常视频没有）
```

- `encv` / `enca` = 样本入口声明「这是加密的」；
- `pssh`（顶层）= 声明了 DRM 保护系统；
- `senc`（每个片段里）= **画面数据本身是密文**。

实测番剧占位流：`pssh=true senc=true encv=true`。
实测普通投稿页：`encv=false avc1=true`，干干净净。

### 第 5 步：回查接口

用 `tools/scan-drm.mjs` 批量看几集番剧，**如果每集返回的清单都一样**，
那就是占位清单而不是你选错了。

## 根因 A：占位流（没有权限）

### 现象

2026-11 实测，匿名访问 4 集番剧，DRM 接口返回的清单**完全一样**：

```
ep=3854802   timelength=1440063   video0 = 32091867755/32091867755-1-100005.m4s
ep=323085    timelength=1440063   video0 = 32091867755/32091867755-1-100005.m4s
ep=469110    timelength=1440063   video0 = 32091867755/32091867755-1-100005.m4s
ep=109726    timelength=1440063   video0 = 32091867755/32091867755-1-100005.m4s
```

`32091867755` 这个 cid **不是这几集番剧的 cid**——
接口给的就是一份「指向别人文件的占位清单」。

### 占位流的完整画像

```
┌─────────────────────────────────────────────┐
│ 番剧 ep3854802 · DRM 接口 · id=112 · 1080P   │
├─────────────────────────────────────────────┤
│ 声明码率      121,552 bps                   │
│ 实际码率      121 kbps（下载后实测）         │
│ 文件大小      21,883,679 字节（20.9 MB）     │
│ 时长          1441 秒（24:00）              │
│ bpp           0.0023（正常应 ≥ 0.04）        │
│ 抽帧画面      纯灰 + 噪点                    │
│ 解码器        error while decoding MB 0 0   │
│               concealing 8160 DC, AC, MV     │
│ 盒子          pssh ✓  senc ✓  encv ✓        │
└─────────────────────────────────────────────┘
```

### 为什么「24 分钟只有 20.9 MB」

因为占位流本身就只有 121 kbps。24 分钟 × 121 kbps ÷ 8 ≈ 20.9 MB —— **完全对得上**。

真实的一集 1080P 番剧，体积应该是它的 15~30 倍。

### 修复

**不要用 DRM 接口的清单下载番剧。**
改用普通播放接口（见 [B 站番剧 DASH 接口](05-bilibili-bangumi.md) 的「扩展的修法：换普通播放接口」一节，以及本页的「修复清单（v1.4.3）」），它给的是真实的流。

## 根因 B：DRM 加密流

### 现象

即使不讨论权限，`ogv/player/pre/check/drm` 返回的流也**带 `widevine_pssh`**，
文件里有 `pssh` / `senc` / `encv` 盒子。

### 为什么表现成「满屏条码」

ffmpeg 用 `-c copy`（不重新编码，直接复制数据）封装时，
会把**加密的采样数据原样搬进 MP4**：

```
加密的 NAL 数据 → MP4（avc1 容器）→ 播放器 → 解不开 → 满屏噪点/条码
```

注意容器是正常的（`avc1`），**坏的是数据本身**。所以文件能打开、时长也对，
但每一帧都是花的——这正是用户描述的「全屏条码」。

### 一个容易漏掉的细节

**音轨不写 `widevine_pssh`。**

实测番剧 DRM 清单里，5 条视频轨都带 `widevine_pssh`（108 字符），
但 3 条音频轨的字段里**根本没有这个字段**——可它们下载下来同样带 `enca` + `senc`。

所以：**只看清单判断不了音轨有没有加密**，只能在下载后看文件。

### 修复

- 下载后体检（`inspectTrackBytes`）：文件头里有 `pssh`/`encv`/`enca`/`senc` → 判为加密；
- 加密的轨道**不作为首选**，自动换下一档；
- 实在没别的可用了，也要明确告诉用户「这一集是加密流，播不了」。

## 根因 C：选错了编码

### 现象

B 站同一个画质会同时给多种编码。实测投稿页 BV11HHq6uEdp 的清单：

```
id=32   854x468   avc1.640033         ← H.264
id=32   854x468   hvc1.1.6.L120.90    ← HEVC（H.265）
id=32   854x468   av01.0.08M.08.0     ← AV1
```

（番剧那边，普通接口也是同样情况：480P 既有 `avc1` 也有 `hvc1`。）

投稿页的清单是怎么取回来的，见 [B 站投稿视频下载](06-bilibili-ugc.md)。

### 两个后果

1. **兼容性**：HEVC / AV1 直接 `-c copy` 装进 MP4，很多老播放器解不出来 → 满屏条纹；
2. **体积**：同样画质，HEVC/AV1 比 H.264 小 30%~50% → 「比实际小」。

### 修复

选轨时**同画质优先 H.264**：

```js
const CODEC_RANK = { avc1: 0, hvc1: 1, hev1: 1, av01: 2, vp9: 3 };
```

并在弹窗里显示编码，让用户知道拿到的到底是什么。

## 根因 D：下载被截断（v1.4.2 已修）

这是老问题，顺带记一笔，因为它和本次的「体积偏小」症状很像：

- 播放器用 **HTTP Range** 分段拉流，嗅探器把**分段**的 `Content-Length` 当成了整个文件的大小；
- 结果列表里显示的大小只有真实值的 1.5%，用户以为下小了。

修法：优先用 `Content-Range` 的总大小（`bytes 0-1023/12345678` → 12345678）。

**分辨方法**：如果文件**能正常播完**但列表里大小很小，是这个问题；
如果文件**播出来是花的**，是加密/占位流问题。

### 新的选轨规则

```
1. 先把「占位流」和「加密流」剔掉
   （万一全被剔光就照旧用它们，但要给出警告）
        ▼
2. 高度上限（设置里选了「最高 720p」之类）
        ▼
3. 画质高的优先
        ▼
4. 同画质时，站点正在播的那一档优先（= 你真正有权看的那一档）
        ▼
5. 同画质时 H.264 优先（兼容性最好）
        ▼
6. 同编码时码率高的优先
```

### 下载后的「体检」

```
下载完一档 → inspectTrackBytes()
   ├─ 文件头有 pssh / encv / enca / senc？ → 加密流
   ├─ 实际码率算出来的 bpp < 0.01？       → 占位流
   └─ 都不是 → 这档能用 ✅
```

不行就换下一档；全都不行就用第一档，并把原因写进任务提示里。

## 番剧页「点单轨下载 403」的四个根因

这一节是 v1.4.3 收尾阶段又挖出来的四个坑，
现象都是「点列表里那条单轨 → 报『所有画质都下载失败（下载失败 403）』」，
而**紧接着下载 DASH 条目却成功**。四个坑叠在一起才造成这个现象。

### 根因 H：番剧页上的轨道和清单根本对不上号

扩展靠**地址完全相同**把「单条轨道」和「DASH 清单」关联起来。
番剧页上这件事经常失败，实测（ep3854802，匿名访问）：

| 来源 | 地址里的 cid | 说明 |
|---|---|---|
| DRM 接口给的清单 | `32091867755` | **属于另一部番剧**的占位清单 |
| 页面真正下载的轨道 | `40394753402` | 这一集的真实轨道 |
| 普通播放接口给的清单 | `40394753402` | 这一集的真实清单（未加密） |

三者的**主机名、签名参数（`upsig`/`trid`/`deadline`）全都不同**，
连文件编号都不一样（`1xxxxx` vs `3xxxx`）。
所以「页面真正下载的轨道」永远关联不上 DASH 父条目，
点它就只会走「裸直链下载」→ CDN 看不到 Referer → 403。

> **修法**：番剧页上，只要是 `.m4s` 轨道（来自 B 站 CDN），
> 一律按「轨道」处理，用普通播放接口的清单重新合成完整视频。
> 判断代码在 `src/background/bilibili-alt.js` 的 `isBangumiTrackItem()`。

### 根因 G：单轨下载只给引擎**一条**候选地址

`convertDashTrack()` 里原来有一句：

```js
videos = same ? [same] : ordered;
if (videos.length > 1) videos = videos.slice(0, 1);   // ← 只留一条
```

于是「最高那一档 403 了」就等于「整单失败」。
DASH 条目那条路没有这个截断（把全部画质都给了引擎），
所以同一个页面里，**DASH 条目能下、单条轨道下不了** —— 这正是当时的现场。

> **修法**：同一画质的排第一，其余画质全部保留作备选，让引擎逐档尝试。

### 根因 F：备用镜像地址没有 Referer 规则

B 站给的每条轨道除了主地址还有一串 `backupUrl`（镜像）。
`installReferers()` 原来只给 `v.url` 装规则，**镜像地址漏掉了**。
而镜像常常在另一个域名上 —— 没有规则就没有 Referer，CDN 直接 403。

> **修法**：`installReferers()` 现在把 `v.url` 和 `v.backups` 一起装规则。

### 根因 E：风控是**按次**的，第一次请求就会被挡

B 站的风控不是「一直不让」，而是「这一次不让」：
同一个接口连着发，第一次可能返回 `data.v_voucher`（要人机验证），
隔一会儿再发就正常了。

原来的 `apiGet()` 只在**后台自取**那条路上重试，
内容脚本那条路只试一次 —— 一旦被挡就直接掉到后台自取，
而后台自取 100% 会撞上风控，等于整条路都废了。

> **修法**：内容脚本那条路也按退避重试，实在联系不上页面才换路。
> 另外备用清单按「标签页 + 集号」缓存 5 分钟，多个条目共用一次接口调用。

### 这四个坑合在一起的现场复盘

```
点「单条轨道」
   ↓
番剧页 → 需要换普通播放接口
   ↓
第一次调接口被风控挡（v_voucher）→ 没换成功
   ↓
回落用占位清单的地址 → 但那是加密流，且镜像没 Referer 规则
   ↓
引擎只拿到 1 条候选地址 → 403 → 「所有画质都下载失败」
```

修完之后（2026-11 实测，ep3854802）：

```
点「单条轨道」→ 换普通接口成功 → 4 档画质逐档试 → 第 1 档就成
              → 合成出 凡人修仙传第178集_480p.mp4
              → 1281.37 秒 / 画面 + 声音都有 ✅
```


### 判定表

| 现象 | 结论 |
|---|---|
| 每集返回的清单都一样，cid 也是别人的 | 占位清单 → 换普通接口 |
| 清单里带 `widevine_pssh` | 加密流 → 换普通接口 |
| 文件里有 `pssh` / `senc` / `encv` | 加密流 |
| 有效码率 < 分辨率应有码率的 1/5 | 占位流 |
| 同一画质有多条轨、编码不同 | 选 `avc1` 那条 |
| 列表里大小小但文件能播完 | Range 分段大小统计错（v1.4.2 已修） |
| 播放是花的但时长对 | 数据是密文或乱码 |

## 经验总结

1. **「下载完成」≠「拿到了视频」。** 必须验证 mime 和体积（v1.4.2 已经开始做）。
2. **「码率最高的」通常不是「最好的」。** 没权限的那一档恰恰标着最高码率。
3. **清单里的 `bandwidth` 可能是假的。** 占位流的 `bandwidth` 只有 121 kbps，
   而正常 1080P 是几 Mbps —— 差了一个数量级。
4. **接口返回 `code: 0` 不代表有数据。** B 站风控会返回
   `data.v_voucher`（人机验证凭证），要退避重试。
5. **同画质多编码时优先 H.264。** 兼容性最好，体积也不吃亏。
6. **JSON 结构不要写死路径。** 同一站点不同页面结构完全不同，要树形搜索。
7. **内容脚本是 classic script，不能 import。** 需要共享逻辑时内联镜像 +
   用单测做「防漂移守卫」（见 `test/dash.test.mjs`）。
8. **下载后一定要再看一次文件。** 清单能说的有限，文件才是事实。
9. **不看图别下结论。** 抽一帧出来看一眼，能省掉很多猜测。
10. **不要用 PowerShell 的 `Get-Content`/`Set-Content` 改中文文件。**
    会按 ANSI 误读、把 UTF-8 改坏（本次踩过一次，表现为 `鐢婚潰鍙栬瘉`）。
11. **「地址对不上」不等于「资源没用」。** 番剧页上页面真正下载的轨道
    和接口给的清单是两个 cid、两套签名，谁也匹配不上 ——
    但那些轨道本身是能下载、能播放的。
12. **风控是按次的，不是按 IP 永久的。** 第一次被挡不代表这条路走不通，
    退避重试比换路更管用。
13. **镜像地址也是地址。** 只给主地址装 Referer 规则，
    镜像一挂就退化成「403」，而且是那种很难查的 403。
14. **给引擎的候选地址要留退路。** 只给一条 = 一次失败就整单失败；
    给全部，引擎就能逐档降级。
15. **报错里一定要带上是哪个地址。** 只有状态码的话，
    「403」这三个字能把你查到崩溃。
