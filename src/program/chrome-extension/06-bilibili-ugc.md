# B 站投稿视频下载

* auto-gen TOC;
{:toc}

B 站上的视频分两类：**番剧**走的是另一套带 DRM 协商的接口，见 [B 站番剧 DASH 接口](05-bilibili-bangumi.md)；而**普通投稿**（用户自己上传的普通视频）走的是完全不同的两条路——`durl` 整段 MP4 和 DASH 清单。本页讲后者。

很多人在投稿页上遇到的是这句话：「这种普通视频没有 DASH，只有片段，下不了完整视频」。这句话**一半对一半不对**：页面确实有 DASH，扩展也确实抓到了，只是常常漏掉播放地址接口的响应；而 B 站接口里那个叫 `durl` 的「分段」，实测**只有 1 段**，而这一段**就是整个视频**。

本页回答三件事：

1. 「没有 DASH」「只有片段」这两个说法，哪里对、哪里不对？
2. 完整视频到底藏在哪个接口里？
3. 我要下它，该怎么操作？

面向零基础。文中每一个数字都是**实测抓取**出来的，不是推测。想自己验证，复现命令见本页「怎么自己复现本页的每个结论」一节；下下来的文件不完整、体积不对、满屏条码，去 [DASH 下载异常排查](09-troubleshooting.md)；整章的阅读路线见 [章节总览](00-summary.md)。

本页出现的 `src/common/download-check.js`、`src/background/bilibili-alt.js` 这类写法，**指的是 video-sniffer 项目里的文件与行号**，不是本章的页面。

1. **「没有 DASH」是错觉。**
   实测这个视频的页面**确实**有 DASH：6 条视频轨 + 3 条音频轨，扩展也抓到了。

## 案例基本信息（实测）

案例：`https://www.bilibili.com/video/BV11HHq6uEdp/`，标题「没有肉车，只有怂人！」。

| 项目 | 值 |
|---|---|
| 标题 | 没有肉车，只有怂人！ |
| BV 号 | `BV11HHq6uEdp` |
| cid | `42431614387` |
| 时长 | 417 秒 |
| 分 P 数 | 1（只有一集） |
| 版权 | 3（转载） |

> **cid 是什么？**
> `cid` 是 B 站给「每一集视频」分配的内部编号。
> 注意 **BV 号和 cid 不是一回事**：
> 一个 BV 号下面可以有好几个 P（分P），每个 P 有自己的 cid。
> 后面会看到，播放地址接口**必须带 cid**，只给 BV 号会直接报错。

## B 站是怎么给播放地址的

### 两个接口，各管一段

```
   ┌──────────────────────────────────────────────────────────┐
   │ 第 1 步：x/web-interface/view?bvid=BV11HHq6uEdp          │
   │         作用：问「这个 BV 号是哪个视频？它的 cid 是多少？」 │
   │         返回：标题、cid、时长、分P 列表                     │
   └──────────────────────────┬───────────────────────────────┘
                              │  拿到 cid
                              ▼
   ┌──────────────────────────────────────────────────────────┐
   │ 第 2 步：x/player/wbi/playurl?bvid=...&cid=...&fnval=... │
   │         作用：问「这个 cid 的播放地址是什么？」             │
   │         返回：播放清单（要么 DASH，要么 durl）              │
   └──────────────────────────────────────────────────────────┘
```

**关键点：第 2 步必须带 cid。**
实测只给 bvid 会返回：

```json
{ "code": -400, "message": "请求错误" }
```

### `fnval` 决定返回什么形态（本章最关键的一张表）

同一个接口，加不同的 `fnval` 参数，返回的东西**完全不一样**。
实测（同一时刻、同一视频）：

| `fnval` | `quality` | `format` | 接口给的是什么 | 视频轨 | 音轨 |
|---|---|---|---|---|---|
| `0` | 16 | `mp4` | **`durl` 数组**（1 段） | — | — |
| `16` | 32 | `flv480` | **DASH 清单** | 4 | 3 |
| `4048` | 32 | `flv480` | **DASH 清单** | 6 | 3 |

> **网页播放器实际用的是 `fnval=4048`**（抓包可见）。
> 它比 `fnval=16` 多给两档编码（AV1），所以扩展默认用 4048，
> 然后自己按「兼容性优先」挑一条。

> **所以「这个视频没有 DASH」是不成立的。**
> 只要 `fnval` 带 16 或 4048，接口就给 DASH。
> 只有 `fnval=0`（最老式的那种调用）才给 `durl`。

### 渐进式接口（`fnval=0`）能拿到多高的画质

这里有个**实测出来的意外收获**。
`fnval=0` 默认给的是 `quality=16`（360p），但加上 `qn` 参数可以要到更高画质：

| 请求的 `qn` | 实际拿到的 `quality` | `format` | 文件大小 |
|---|---|---|---|
| 16 | 16（360p） | `mp4` | 46.4 MB |
| 32 | 16（360p） | `mp4` | 46.4 MB |
| **64** | **64（720p）** | `mp4720` | **99.6 MB** |
| 80 | 64（720p） | `mp4720` | 99.6 MB |
| 116 | 64（720p） | `mp4720` | 99.6 MB |

**注意最后一行：这个视频的 DASH 上限是 480p，而渐进式接口能给到 720p。**
下载下来的成品实测分辨率是 **1280x702**（720p 档），
而 DASH 那条路是 **854x468**（480p 档）。

> ⚠️ **别把这两个数字记混**：
> - `quality` / `qn` = 画质档位编号（16=360p、32=480p、64=720p、80=1080p、116=4K）
> - 音轨的 `id`（30216 / 30232 / 30280）= **音频清晰度编号**，跟画面画质无关。
> - 文件名里的数字（`30032`、`100022`）= B 站的**内部文件编号**，
>   **不是画质**。详见上文「一个必须知道的坑：文件编号 ≠ 画质」。

## 「片段」到底是什么

### 三种长得像、含义完全不同的东西

这是本章最需要分清的地方。用户界面上一眼看去都是「一条一条的地址」，
但它们根本不是一回事（三种形态的一般性介绍见 [音视频基础](02-media-fundamentals.md)）：

| | **① MSE 缓冲片段** | **② DASH 轨道（.m4s）** | **③ `durl` 分段** |
|---|---|---|---|
| 长什么样 | 一堆几百 KB 的小块 | 每条几百 KB～几十 MB | 每条几十～一百 MB |
| 是什么 | 播放器**边播边下**的缓冲数据 | 只有画面或只有声音的**一条轨** | **一整段视频**（可能整个视频就一段） |
| 有没有声音 | 有画面**也有**声音（已解封装） | **没有**（视频轨）或**没有**（音频轨） | 有画面**也有**声音 |
| 能不能单独播 | 勉强能，但只是片段 | 不能（只有一半） | **能，就是完整视频** |
| 扩展里叫什么 | 「缓冲片段」 | 「DASH 的单条视频轨 / 音频轨」 | 「整段视频」 |

**你说的「只有片段」，大概率是看到了 ①。**
① 是播放器实时缓冲的产物，下多少是多少，**天然不是完整视频**。

### 扩展实测登记了什么

用 CDP 打开这个页面、让扩展嗅探一遍，**实测登记了 5 条**：

```
[dash]    https://upos-sz-mirrorhw.bilivideo.com/upgcxcode/87/43/42431614387/424…  video/mp4
[blob]    blob:https://www.bilibili.com/e6f874ee-1b02-4e60-8a11-f11d6ab74284
[segment] https://upos-sz-mirrorcos.bilivideo.com/upgcxcode/87/43/42431614387/42…  ×3
```

- 1 条 `dash` = 完整的 DASH 清单（6 视频轨 + 3 音轨，417 秒）→ **这才是完整视频的来源**
- 1 条 `blob` = 播放器的内存句柄（不是文件）
- 3 条 `segment` = 缓冲碎片（噪音，默认隐藏）

所以扩展**本来是抓到 DASH 的**。问题出在「有时候抓不到」（见下文「那为什么还是「下不了完整视频」？」）。

### 一个必须知道的坑：文件编号 ≠ 画质

`fnval=4048` 给的 6 条视频轨，实测长这样：

| 画质 `id` | 分辨率 | 编码 | 码率 | 文件名 |
|---|---|---|---|---|
| 32 | 854x468 | `avc1.640033`（H.264） | 878020 | `42431614387-1-30032.m4s` |
| 32 | 854x468 | `hvc1.1.6.L120.90`（HEVC） | 475582 | `42431614387-1-30033.m4s` |
| 32 | 854x468 | `av01.…`（AV1） | 479773 | `42431614387-1-100023.m4s` |
| 16 | 640x350 | `hvc1.1.6.L120.90` | 326345 | `42431614387-1-30011.m4s` |
| 16 | 640x350 | `avc1.640033` | 862521 | `42431614387-1-30016.m4s` |
| 16 | 640x350 | `av01.…` | 328940 | `42431614387-1-100022.m4s` |

**看两件事：**

1. **同一个画质，文件名编号各不相同**（468p 的三条是 `30032` / `30033` / `100023`）。
   编号 `3xxxx` 是老编码（H.264 / HEVC），`1xxxx` 是新编码（AV1）。
2. **编号大小和画质无关**。`30016`（350p）和 `30032`（468p）编号挨着，
   但分辨率不同；`100023` 编号更大，画质却和 `30032` 一样。

👉 **想判断画质，只能看 JSON 里的 `height` 字段，不能看文件名。**

> 这个坑的另一个后果：**「播放器实际在下载的 URL」≠「清单里列的 URL」**。
> 页面上真正请求的那条，和接口清单里某一条，可能只是编码不同、编号不同。
> 扩展 v1.4.3 之前靠「URL 完全相同」把单轨和 DASH 清单配对，
> 在这种情况下就配不上 → 点单轨下载 → CDN 403。
> 番剧页那次的四个根因之一就是它（详见 [DASH 下载异常排查](09-troubleshooting.md) 里关于「点单轨下载 403」的四个根因）。

## 实证：`durl` 那一项就是整个视频

### 盒子结构

MP4 文件是由一个个「盒子（box）」串起来的。实测把 `durl` 那一项整个下载下来（46.4 MB），
扫它的前几个盒子：

```
ftyp(32)  moov(517599)  free(8)  mdat(48113746)
```

| 盒子 | 含义 | 实测大小 |
|---|---|---|
| `ftyp` | 文件类型（这是 MP4） | 32 字节 |
| `moov` | **索引信息**：时长、分辨率、码率、音轨表，全在这儿 | 517 KB |
| `free` | 占位 | 8 字节 |
| `mdat` | **真正的媒体数据**（画面+声音） | 48.1 MB |

**关键判据：整份文件里有 `moov`，而且没有 `moof`。**

- 有 `moov` → 这是一个**自带索引的完整文件**，播放器能从头找到尾。
- 有 `moof`（fragment box）→ 这是 fMP4 **碎片**，必须靠拼接或合并才能播。

### 由此得出两条结论

**结论一：这个 `durl` 项是完整的，46.4 MB 就是整个视频。**
不是「下到一半」，也不是「只有开头」。

**结论二：这种文件绝不能按字节顺序拼。**
如果 `durl` 真的有多段（比如 B 站把超长视频拆成几段），
每段都自带一份 `moov`。按字节拼起来，播放器只会读到**第一段的索引**，
后面全是垃圾 —— 表现就是「下下来的视频只有开头一小段」。

正确做法是用 ffmpeg 的 **concat 分离器**：

```
ffmpeg -f concat -safe 0 -i concat.txt -c copy 输出.mp4
```

扩展 v1.4.4 加了自动判别（`src/common/download-check.js` 的 `looksLikeStandaloneMp4()`）：
扫前几个盒子，`ftyp + moov + mdat` 且**没有** `moof/styp` → 判定为「独立完整 MP4」，
走 ffmpeg 合并；否则按 fMP4 碎片处理，按字节拼。

## 那为什么还是「下不了完整视频」？

既然地址是有的、清单也是完整的，失败点一定在**从清单到成品**这一段。
排查下来是 5 个独立的坑：

### 坑 1：扩展没抓到播放地址接口的响应（最常见）

扩展靠「页面钩子」拦截 `x/player/wbi/playurl` 的响应。
钩子装在页面主世界里（主世界 / 隔离世界的分工见 [扩展架构](03-architecture.md)），
下面几种情况会漏：

- 页面在**装扩展之前**就打开着 → 内容脚本压根没注入；
- 页面走了 Service Worker 或别的方式取数 → 钩子没拦到；
- 响应命中了**浏览器缓存** → 网络层看不见。

漏掉的症状非常典型：**列表里只剩「缓冲片段」**，用户看着一堆碎片，却下不到完整视频。

👉 **v1.4.4 的修法**：popup 里加一个「**补抓播放地址**」按钮，
让扩展**自己**去接口要一份清单，插回列表。
走的是内容脚本代发那条路（见下文「扩展这一版（v1.4.4）改了什么」一节）。

### 坑 2：只给 bvid 不给 cid

播放地址接口必须带 cid，只给 bvid 直接 `-400 请求错误`（实测）。
扩展的补抓流程因此是两步：`bvid → view 接口 → cid → playurl`。

### 坑 3：`durl[].length` 的单位是毫秒

接口给的是 `length: 416816`，意思是 **416.816 秒**。
扩展 v1.4.3 之前把它当成秒用，时长变成 416816 秒（约 116 小时），
完整性校验（下载大小 vs 预期时长）也跟着废掉。
v1.4.4 修成毫秒→秒。

### 坑 4：多段 durl 按字节拼

见上文「由此得出两条结论」。v1.4.4 改成自动判别 + ffmpeg concat。

### 坑 5：CDN 要 Referer，下载请求带不上

B 站 CDN 校验 `Referer`，没有就返回 403 + 一个几百字节的 HTML 错误页。

而 `chrome.downloads.download()` **不会带 Referer**（Referer 是 fetch 的禁止头），
`declarativeNetRequest` 的规则也覆盖不到下载请求（三种规则写法实测全部无效）。

这条是历史遗留的老问题，扩展早就绕开了（下载走引擎自己发请求，不是走 chrome.downloads）。
**但如果你要自己写脚本下载，千万别忘了带 Referer** —— 下文「自己写脚本下载（原理版）」的脚本已经带上了。

## 三条完整的下载路线（全部实测过）

### 路线 A：扩展的「补抓播放地址」按钮（推荐给扩展用户）

1. 打开 B 站视频页；
2. 点扩展图标；
3. 如果列表里**没有**「完整视频」条目，popup 会自动显示「**补抓播放地址**」按钮；
4. 点它，扩展自己去接口要清单；
5. 列表里会多出「DASH 视频+音频（手动补抓）」和/或「整段视频（手动补抓）」；
6. 点「下载」。

**实测结果**（BV11HHq6uEdp）：

```
PASS  补抓播放地址能拿到完整清单（视频轨 + 音轨）
PASS  补抓到的清单能下载出完整视频
  补抓下载: 没有肉车，只有怂人！_468p.mp4
```

产物实测：51.25 MB，416.82 秒，854x468，H.264 + AAC 立体声，**音画俱全**。

### 路线 B：完全不用扩展 —— `tools/download-ugc.mjs`（推荐给不想装扩展的人）

项目里带了一个现成的脚本，**不需要装任何东西**（连 ffmpeg 都不用装，
用的是项目自带的 `@ffmpeg/core`）。

```powershell
# 默认模式：渐进式（整段 MP4），画质反而最高
node tools/download-ugc.mjs BV11HHq6uEdp

# DASH 模式：画面/声音分开下载再合成
node tools/download-ugc.mjs BV11HHq6uEdp --mode dash

# 只看清单不下（先看看能拿到什么）
node tools/download-ugc.mjs BV11HHq6uEdp --dry-run

# 指定输出目录 / 分P
node tools/download-ugc.mjs BV11HHq6uEdp --out D:\Videos
node tools/download-ugc.mjs BV11HHq6uEdp --p 2
```

**实测结果**：

```
# 渐进式
[ugc] durl: 1 段  画质=64 (mp4720)  总时长=416.8s  总大小=99.6 MB
[ugc] 只有 1 段 —— 它本身就是完整视频，直接存。
[ugc] 完成: …\没有肉车，只有怂人！_64p.mp4  (99.6 MB)

# DASH
[ugc] DASH: 6 视频轨 / 3 音轨  画质=32 (flv480)  时长=417s
[ugc] 选中: 视频 854x468 avc1.640033 / 音频 mp4a.40.2
[ugc] 用 ffmpeg 合成…
[ugc] 完成: …\没有肉车，只有怂人！_468p.mp4  (51.2 MB)
```

## 自己写脚本下载（原理版）

### 第 1 步：拿 cid

```bash
curl -s "https://api.bilibili.com/x/web-interface/view?bvid=BV11HHq6uEdp" \
  -H "Referer: https://www.bilibili.com/video/BV11HHq6uEdp/" \
  -H "User-Agent: Mozilla/5.0"
```

返回的 `data.cid` 就是 cid（`42431614387`），`data.title` 是标题。

### 第 2 步：拿播放地址

```bash
curl -s "https://api.bilibili.com/x/player/wbi/playurl?bvid=BV11HHq6uEdp&cid=42431614387&fnver=0&fnval=0&fourk=1&qn=64" \
  -H "Referer: https://www.bilibili.com/video/BV11HHq6uEdp/" \
  -H "User-Agent: Mozilla/5.0"
```

想用 DASH 就把 `fnval=0` 换成 `fnval=4048`，并去掉 `qn`。

### 第 3 步：下载

**从返回的 JSON 里取出 `data.durl[0].url`（或 DASH 里的 `data.dash.video[].baseUrl`），然后：**

```bash
curl -L -o 视频.mp4 "<取出来的地址>" \
  -H "Referer: https://www.bilibili.com/video/BV11HHq6uEdp/" \
  -H "User-Agent: Mozilla/5.0"
```

> ⚠️ **Referer 一定要带**，否则 CDN 返回 403 + 一个几百字节的 HTML 错误页。
> 那个文件扩展名还是 `.mp4`，双击打不开，很容易误以为是「下坏了」。

> ⚠️ **地址是带签名、有有效期的**，过一会儿就失效。所以不能把地址存下来过几天再用，
> 要用的时候重新调一次接口。

DASH 路线还要把视频轨和音频轨用 ffmpeg 合成：

```bash
ffmpeg -i video.m4s -i audio.m4s -c copy -movflags +faststart 输出.mp4
```

## 常见误判速查

| 你看到的 | 真实原因 | 怎么办 |
|---|---|---|
| 列表里一堆几十 KB 的碎片 | 那是 MSE 缓冲片段，本来就只是缓冲 | 点「补抓播放地址」 |
| 列表里只有「DASH 的单条视频轨」 | 清单抓到了，但音轨没配对 | 用「补抓播放地址」拿完整清单 |
| 下下来的文件几百字节、打不开 | CDN 返回了 403 错误页（缺 Referer） | 下载请求必须带 Referer |
| 下下来的视频只有开头一小段 | 多段 durl 被按字节拼了 | 用 ffmpeg concat 合并 |
| 时长显示成 116 小时 | `durl.length` 是毫秒不是秒 | 毫秒 ÷ 1000 |
| 接口报 `-400 请求错误` | 只给了 bvid 没给 cid | 先调 view 接口拿 cid |
| 明明是 720p，DASH 里只有 480p | 两条路给的上限不一样 | 试试 `fnval=0&qn=64` |
| 按文件名猜画质猜错了 | 文件编号跟画质无关 | 看 JSON 里的 `height` |

体积不对、满屏条码、403 这类更麻烦的症状，去看 [DASH 下载异常排查](09-troubleshooting.md)。
